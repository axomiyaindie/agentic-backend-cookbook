# Idempotency

**Idempotency** means: running the same operation twice has the same
effect as running it once.

The canonical example is a payment. A user clicks "Pay $50". The request
reaches the server, the server charges the card, and then the response is
lost on the way back (network blip, user closed the tab, load balancer
restarted). The client retries. **Without idempotency, the user is charged
$100.** With idempotency, the second request returns the same result as
the first — the user is charged $50 exactly once.

## The one idea to take away

Transactions and idempotency solve **different** problems:

| | Transaction | Idempotency |
|---|---|---|
| Protects against | A step **inside** the request failing | The **whole request** being retried |
| The bug it fixes | Debit ran, credit didn't | The same charge ran twice |
| The fix | `BEGIN … COMMIT … ROLLBACK` | `Idempotency-Key` header + a `seen_keys` table |

A transaction says "all of these statements or none of them". Idempotency
says "this operation, even if you ask twice, happens once".

You need **both**, because they protect against different failure modes.

## Why this matters more for AI backends

AI apps are retry-heavy for one specific reason: **model calls are slow
and unreliable.** A call to OpenAI can take 30 seconds and time out. A
call to an MCP tool can hang. The client (or your own job runner)
retries. If the operation was "charge the user for this AI completion,"
you just charged them twice.

Other AI-flavored retry triggers:

- **Job queues** — background jobs retry after failure (see
  [`11-background-jobs/`](../11-background-jobs/)). Every retry hits your
  handler again.
- **Agent loops** — an agent may decide to call the same tool twice in one
  turn, or re-run a step after a transient failure.
- **Webhooks** — most webhook providers (Stripe, GitHub, OpenAI) *retry*
  until your endpoint returns 200. If your endpoint isn't idempotent, you
  process the event multiple times.

Every one of those cases is the same problem: **the same logical operation
arrives more than once, and you need to make it happen once.**

## The mechanism

The standard pattern — used by Stripe, and the one this lesson
implements — is:

1. The client sends an `Idempotency-Key: <uuid>` header with the request.
2. The server looks up that key in a `seen_keys` table.
3. **If the key is present** → return the stored response. Do **not** run
   the handler again.
4. **If the key is not present** → run the handler, store the response
   under the key, return it.
5. On every retry, step 3 fires. The operation happens once.

The `Idempotency-Key` is usually **generated by the client** (or by the
SDK), not the server, because the client is the one that knows when it's
retrying.

## The states of a key

A `seen_keys` row moves through states:

| State | Meaning |
|---|---|
| `in_progress` | A request with this key is currently being processed |
| `completed` | A prior request with this key returned successfully |
| `failed` | A prior request with this key returned an error |

When a **second** request arrives with the same key:

- `completed` → return the stored response verbatim. Same status, same body.
- `failed` → let the request proceed again (the prior attempt failed, so
  a retry is safe).
- `in_progress` → reject with **409 Conflict**. A concurrent duplicate is
  arriving. Real systems either wait or return "still processing".

## Lesson

`01-fastapi-idempotency/` — a FastAPI + SQLite app with:
- `POST /charge` — charges a (fake) card, protected by idempotency
- `GET /charges` — shows every charge that actually happened
- `POST /reset` — clears the database, so you can re-test

The README walks you through sending the **same** charge request three
times with the **same** `Idempotency-Key`. Only one charge happens. Then
you send it with a **new** key and a second charge appears.

## Where this fits in real code

- **Stripe** — the original reference implementation. Their docs on
  idempotency are worth reading.
- **Square, PayPal** — same pattern, same header name.
- **Webhook receivers** — dedupe on the provider's event ID (often the
  same idea, different header name).
- **Job queues** — retried jobs need idempotent handlers, whether the
  handler implements its own keys or the queue provides them (SQS FIFO
  does).
- **AI SDKs** — some support idempotency headers. If yours does, use it.
  If it doesn't, wrap the call in your own idempotency layer.

## What this lesson does not cover

- **Concurrent requests with the same key.** This lesson returns 409 for
  `in_progress` keys but does not block. Production systems often hold a
  lock until the first request completes. Both are valid; blocking is
  harder.
- **Key expiration.** `seen_keys` grows forever. Real systems delete
  rows after 24 hours (Stripe's default). The lesson keeps everything
  to make the demo simple.
- **Response expiry.** If the stored response is 5 MB of JSON, storing
  it is expensive. Stripe truncates. The lesson stores the full body.
- **Hashing the body.** The server should verify that a retried key comes
  with the *same body*. If key `abc` is first used for `charge=$50` and
  later for `charge=$500`, that's a bug in the client. Stripe rejects
  this with a 422. The lesson does not enforce it.

Each of those is worth its own lesson eventually. The mechanism in this
lesson — key + table + return-stored-response — is the seed of all of
them.

## In another language?

The pattern is identical in every language. What changes is the storage
backend and the framework hook:

| Language | Storage | Framework hook |
|---|---|---|
| Python (FastAPI) | SQLite / Postgres / Redis | A dependency or middleware |
| Go | Same, via `database/sql` | A middleware wrapper |
| Rust | `sqlx` / `redis` crate | axum middleware / extractor |
| Node | Prisma / ioredis | Express middleware / Fastify hook |
| PHP | Laravel Cache / MySQL | A middleware group |
| Ruby | ActiveRecord / Redis | `before_action` in a controller |
| Java | JDBC / Redis (Lettuce) | Spring filter / interceptor |
| C# | EF Core / Redis | ASP.NET action filter |

The mechanics are the same everywhere: read the header, look up the key,
short-circuit on hit, store on miss. If you understand why the lesson's
`/charge` only charges once, you can build idempotency in any language.
